# pirc の設計

## 目的とスコープ

pirc は、起動中の pi TUI セッションを別端末のブラウザから閲覧・操作するためのアプリケーション。携帯回線でも使える通信量を目指す。

- ブラウザから履歴と生成中の内容を閲覧し、メッセージ送信・中断・モデル切替などを行う。
- 接続中の pi プロセスから新しい空セッションを作成したり、保存済みセッションへ切り替えたりできる。Web からの pi プロセス起動や、pi を介さない休止セッションの閲覧は対象外。
- 他 extension の TUI ダイアログは Web に転送しない。ダイアログ待ちであることのみ表示する。
- 認証は提供せず、外部公開時のアクセス制御は前段の reverse proxy 等に委ねる。

## 構成と責任分界

```text
pi TUI ─ pi-extension ── WS ── server ── WS / HTTP ── frontend
          状態の観測・操作         中継・射影          表示・入力
```

- **状態の正本は pi プロセス**。server はセッションを永続化せず、frontend も独自の正本を持たない。切断・再起動後は pi から再同期できること。
- extension はセッションを観測して同期操作を送り、ブラウザからの操作を pi API に渡す。接続は pi から server、ブラウザから server への方向で開く。
- server は接続中セッションの登録・中継と、購読者ごとの表示用データの射影を担う。送信先によって必要な情報量を変えても、pi の状態は変更しない。
- frontend は受け取った同期操作で表示を更新する。操作の送信時に履歴や生成結果を楽観的に書き換えない。

server は購読開始時の現在値を配信するため、接続中セッションの実行状態と未確定のツール詳細を一時的に保持する。このミラーは pi から再構築するもので、履歴の保存先や独立した正本にはしない。ブラウザごとの購読管理は server の責任とし、extension に持ち込まない。

主要な配置は `api/`（共有契約・通信）、`pi-extension/`（観測・操作）、`server/`（中継・射影）、`frontend/`（表示・入力）。開発・起動方法は `README.md` を参照。

`api/` の TypeScript ソースは三者が直接共有し、独立したビルド成果物を持たない。通信契約の正本は `api/src/`、各ランタイムの依存関係・設定の正本はそれぞれの設定ファイルとする。

## 同期モデル

pi の session entry は親子関係を持つ履歴で、append 済みの entry は不変。leaf は現在の枝の末端であり、active branch は leaf から親を辿った表示対象の履歴を指す。leaf は entry の追加を伴わずに移動することもある。

pi の extension event だけでは entry の追加を網羅できない。event が届く時点ではまだ entry が追加されていない場合や、対応する event がない追加もあるため、extension は pi の session manager と照合して履歴を同期する。pi API から観測できないもの（キュー中メッセージの内容など）は表示対象にしない。

extension は pi の event 自体ではなく、クライアントのミラーに適用できる同期操作を送る。次の区別を保つ。

- **確定した履歴**は entry として送る。取りこぼしは差分同期で回復する。
- **生成中の内容・ツール進捗**は WS で現在値と更新を送る。購読開始・復旧時の現在値は server の一時ミラーから配信する。
- 表示中の枝だけが履歴全体ではない。ブラウザは必要な過去の枝を後から取得できる。

同期操作とスナップショットの型・適用規則は `api/src/sync.ts` と frontend の mirror 実装を参照。

### 履歴と実行状態の同期

HTTP の `/sync` は確定履歴だけを扱い、生成中メッセージ、ツール進捗、セッション状態は含めない。実行状態はセッションの WS 購読開始時に現在値を受け取り、その後の更新を適用する。履歴の取得中も実行状態の更新は止めず、HTTP 応答で新しい実行状態を巻き戻さない。

購読開始と履歴スナップショット取得の間にも操作は発生する。取りこぼしを防ぐため、**購読を登録してから履歴スナップショットを取得**し、その間の操作を履歴用にバッファする。履歴にはスナップショットの sequence 以下の操作を重ねず、残りを順に適用する。実行状態は WS の現在値を境界として独立に更新する。不連続やカーソル不整合が起きた場合は購読の現在値と履歴を取り直して復旧する。

初回同期は現在の active branch の必要な範囲を取得し、続きは要求時に遡る。再接続時は既知の entry の位置から差分を取得できる。sequence の管理と同期の具体的な境界条件は extension・server・frontend の実装を正本とする。

### 射影と通信量

server はツール関連 entry と生成中の tool call を表示用の最小情報に射影する。思考内容は省略しない。展開したツールの詳細は、セッション全体の表示プロファイルではなく、ツール ID ごとの購読として扱う。展開のたびに履歴を再同期したり、展開中の ID 一覧を HTTP query に渡したりしない。

frontend は省略された履歴と詳細オブジェクトを別々に保持し、表示時にツール ID で結合する。詳細を履歴の正本に混ぜないため、履歴再同期で省略 entry が届いても、取得済みの確定した詳細は失われない。HTTP で取得した不変の entry 全文も同様に別に保持する。

射影の対象と表示用データの形は `api/src/projection.ts` と `server/core/projection.ts` を正本とする。

### ツール詳細の購読と終端

実行中の詳細を展開すると、server は **現在値 → 差分 → 終端** の順に配信する。引数生成中から同じツール ID を使い、assistant entry の確定やツール実行への移行で購読を作り直さない。詳細には引数、途中の内容、確定結果を含める。大きな文字列は既知の部分を再送せず、追加・訂正部分を差分として送る。

購読開始時の現在値と以後の差分には revision の境界を設ける。再購読には別の購読識別子を使い、古い購読の遅延通知を新しい状態へ混ぜない。差分が不連続なら対象オブジェクトだけを再購読し、セッション履歴の再同期には広げない。

**終端は実行終了イベントではなく、完全な確定結果が揃ったことの保証**。pi の不変な tool result entry を観測した後、途中の内容と確定結果の違いを配信してから終端を送る。終端以降、その entry の HTTP 取得結果は安定している。server と frontend は対象の購読を内部的に終了し、frontend は受信済みの詳細を確定データとして保持する。server は完了した詳細の全文を保持し続けない。

終端まで受信した詳細は、確定履歴が省略 entry として届いても再 GET しない。未購読の完了済み詳細や、途中で切断して完全性を確認できなかった詳細は、必要に応じて HTTP で取得する。完了直前に購読した場合も、購読開始時点で既に完了していれば HTTP へ移る。確定結果のない中断を、完全な結果がある終端として扱わない。

契約は `api/src/objects.ts`、server の一時ミラーは `server/core/runtime.ts`、履歴と詳細の表示用結合は frontend の mirror と tool view を参照する。通信量の削減によって再同期可能性を失わないこと。

### セッションの同一性

pi の sessionId は、ブラウザが接続先を識別するための一意なキーではない。同じ sessionId を複数の pi プロセスが開くことがあるため、接続中のセッションは instanceId で区別し、同一 pi プロセス内でのセッション切替の追跡には hostId を使う。

一時的な通信切断と、pi でのセッション切替は別物として扱う。一時切断からの再接続では同じインスタンスを再同期し、セッション切替では別インスタンスとして扱う。`/reload` では同じセッションを継続できるよう、同一性と同期の sequence を引き継ぐ。

## 通信と操作

pi と server、ブラウザと server はそれぞれ WS で接続する。履歴のスナップショットや必要な箇所の取得には HTTP も使う。通信の型と経路は `api/src/host-protocol.ts`、`api/src/client-protocol.ts`、`api/src/http.ts` を正本とする。

- WS のメッセージは JSON-RPC を基本とし、大きいメッセージは gzip で送る。受信側は両形式を扱い、受信順に適用する。
- server が遅い購読者へ際限なく操作を積まず、必要なら再同期を促す。負荷制御は他の購読者や pi の状態を巻き込まない。
- ブラウザからの操作は server が extension に中継する。受理と pi での処理完了が異なる操作は、後から失敗を通知できるようにする。

## 画面と再同期

ブラウザには接続中セッションの一覧と、セッションの履歴・生成中の内容・入力欄を表示する。表示対象の枝が変わり、必要な entry が手元にない場合は取得して補う。確定済みの entry は再利用できる。

一覧の message preview は一覧を開いたときに HTTP で取得する。WS で配信する一覧の変更は、追加・削除と、名前・モデル・実行状態などのメタデータに限定する。変更のないセッションや preview の本文を全更新のたびに再送しない。個別セッションの実行状態にも一覧用の preview は含めない。

WebSocket の再接続、server からの再同期要求、ブラウザが非表示になった後の復帰でも、pi の状態に追いつけること。画面構成と表示の細部は `frontend/` を正本とする。

HTTP で配信される場合もあるため、ブラウザの secure context 限定 API を必須にしない。

## トランスポートとアクセス制御

server 自体は認証を持たない。外部公開時には reverse proxy 等でアクセスを制御する。ブラウザ用 WS では他サイトからの接続を制限する一方、pi からの接続はブラウザの Origin と同じ前提で扱わない。

provider の認証ヘッダや system prompt を通信に載せない。ただし会話内容とツール出力（ファイル内容を含む）は server を通るため、server とその接続経路は機密データを扱うものとして運用する。
